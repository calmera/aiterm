# DECISIONS — choices this build made where the spec left room

Each entry: what was decided, and one line of reasoning.

1. **ESP-IDF v6.0.2** — the version pinned by `tanmatsu-template`'s Makefile and required (`idf: ">=6.0.2"`) by badge-bsp/tanmatsu-wifi. Toolchain `riscv32-esp-elf` esp-15.2.0_20251204.
2. **All components vendored into `components/`, component manager disabled** — the Espressif component registry (components.espressif.com / api.components.espressif.com / components-file.espressif.com) and dl.espressif.com are blocked from this build host; GitHub git clones and release assets work. Sources and commits are listed in `components/VENDORED.md`. Requirements the component manager would have injected were added to the vendored CMakeLists by hand.
3. **badge-bsp v1.6.1** (not the template's 1.1.0) — the version the reference launcher ships with and the one with the storage API the spec mentions (>=1.6); tanmatsu-wifi 1.3.1 accepts >=1.1.0.
4. **esp-hosted fork `Nicolai-Electronics/esp-hosted-mcu` tag v2.12.3-1** — this is `nicolaielectronics/esp-hosted-tanmatsu 2.12.3~1`, the exact version tanmatsu-wifi 1.3.1 pins; it carries the "reset slave using callback" patch the badge needs. The C6 firmware is never touched.
5. **`CONFIG_BSP_TARGET_WHY2025` + the WHY2025 SDIO pin map** from `tanmatsu-template/sdkconfigs/why2025` (CMD 33, CLK 32, D0 28, D1 31, D2 30, D3 29) — the WHY2025 badge routes the C6 differently from the Tanmatsu.
6. **Console on UART0** — originally USB-Serial/JTAG because the spec said USB-C goes there. On the real WHY2025 badge the side USB-C is a CH340 on UART0 (GPIO37/38) and the P4 USB-Serial/JTAG is not wired out, so the console was moved to UART0 (2026-10-17). The bottom USB-C is the ESP32-C6's USB-Serial/JTAG (303a:1001), not the P4's.
7. **`storage` partition is SPIFFS, not LittleFS** — ESP-IDF has SPIFFS built in; LittleFS is a registry component (joltwallet) that would have needed another vendored tree. It only holds the MCP tool-list cache.
8. **Wi-Fi credentials live in the app's own NVS JSON config (`aiterm/config`), with `wifi_init_config.nvs_enable = false`** — the ESP-Hosted slave would otherwise persist credentials in the C6's NVS; the launcher/wifi-manager do the same.
9. **LVGL 9.4.0, RGB888 (24 bpp), partial render into two PSRAM draw buffers, software rotation 90° via `lv_display_rotate_area` + `lv_draw_sw_rotate`, flushed with `bsp_display_blit`** — follows the launcher's pipeline (BSP RGB888 DPI framebuffer, rotation 90 == pax CCW); LVGL's ROTATION_90 pixel mapping was verified to equal pax's CCW mapping.
10. **Font: DejaVu Sans Mono converted with lv_font_conv** at 13/15/18 px (small/medium/large; medium gives exactly 80 columns at 720 px) plus bold variants for headings — DejaVu Sans Mono is available on the build host and covers Latin-1 + box drawing.
11. **Meta key = the badge's SUPER (⌘-like) key** — the WHY2025 BSP reports it as `BSP_INPUT_MODIFIER_SUPER_L`, so `Meta+M`, `Meta+N`, `Meta+,` are Super combinations.
12. **PgUp/PgDn/Home/End = Fn+Up/Down/Left/Right** — the keyboard has no dedicated keys; the BSP exposes an Fn modifier.
13. **Provisioning SoftAP is open (no PIN)** — the Wi-Fi QR then joins without typing anything (`WIFI:T:nopass;S:aiterm-XXXX;;`); the AP only exists during setup and only exposes the setup page. The spec allowed either; a PIN would add a second thing to type on a phone.
14. **Provisioning page never leaves the device: a single embedded HTML file, no frameworks** — served at `http://192.168.4.1/` on the hotspot and at `http://<station-ip>/` once connected. Secrets are masked (`••••abcd`) in `GET /api/config`; a masked value posted back keeps the stored secret.
15. **MCP tool cache in SPIFFS (`/storage/mcp_<index>.json`)** — loaded before the live `initialize`/`tools/list`, so tools are present immediately after boot; replaced on a successful refresh.
16. **Tool names sent to the model are `<server>__<tool>`**, with the server name sanitised to `[A-Za-z0-9_-]` (OpenAI rejects other characters).
17. **In the SSH terminal, Esc is sent to the remote** (vim and friends need it); the view is left with `Meta+Q` or `Meta+Esc`, or with Esc once the connection has closed. Everywhere else Esc closes the view / cancels the request as specified.
18. **SSH host keys are not pinned** — there is no known_hosts store on the badge; the SHA-256 fingerprint is logged on the serial console at each connect. Password auth only, as specified.
19. **SSH uses wolfSSH 1.4.20 + wolfCrypt 5.8.2, not libssh2** — ESP-IDF 6.0.2 ships mbedTLS 4.1 (TF-PSA-Crypto 1.0), which removed the legacy `mbedtls_ecdh_*`, `mbedtls_pk_rsa()`/`mbedtls_pk_ec()` and `MBEDTLS_ECDSA_C`-style configuration that libssh2's mbedTLS backend (even upstream master) is written against; porting libssh2 to PSA was out of budget. The `sshterm` reference app for this badge already uses wolfSSH/wolfSSL with a `user_settings.h`, so that stack was vendored from the reference tree (software crypto, client only, custom lwIP socket I/O). Enabled by `CONFIG_AITERM_SSH` (default y). wolfSSL/wolfSSH are GPLv3 (or commercial) — see `components/wolfssl/LICENSING`.
20. **Anthropic API version header `2023-06-01`** — the spec's `2023-06-18` is not a published version string; `2023-06-01` is the current GA value and supports tools, streaming and `system`.
21. **Streaming requests use HTTP/1.1 with `esp_http_client`, one connection per request (no keep-alive)** — simplest reliable path for SSE on lwIP; the handshake cost (~1 s) is paid once per turn/tool round.
22. **Text deltas are coalesced (48 bytes or 60 ms) before being posted to the UI task** so single-token SSE events do not flood the LVGL task queue.
23. **Phone-side JSON export is unformatted and small enough for a QR code** for typical configs (one endpoint, a few servers); the page has no QR scanner, as allowed by the spec.
24. **Markdown rendering uses `lv_spangroup` per block** (bold runs in DejaVu Sans Mono Bold, inline code in the string colour); code/diff/table views render monospace rows with LVGL label recolor (`#RRGGBB text#`), which LVGL 9.4 supports again.
25. **Download-mode key not quoted in README** — docs.tanmatsu.cloud, wiki.badge.team and the WHY2025 badge sites are blocked from this build host, and none of the cloned repos (template, launcher, BSP, BadgeVMS) document the key. The README gives the generic "hold BOOT, tap RESET" sequence and points at the badge wiki rather than inventing a pin.
26. **Optional components declare their requirements unconditionally in CMakeLists** — IDF collects component requirements before Kconfig is evaluated, so a `PRIV_REQUIRES` inside `if(CONFIG_AITERM_SSH)` was silently dropped (the libssh2 attempt failed with "mbedtls/version.h not found"). Only the source lists are gated on the option (wolfssl, wolfssh).

27. **Rooms mode is a chronicle-agents client in the firmware, speaking NATS** — chronicle has no HTTP data API (everything is request/reply and JetStream on NATS), so the badge gained a NATS client beside its HTTP ones. `components/espidf-nats` (debsahu/espidf-nats 1.4.0, header-only C++, mbedTLS, JetStream) is vendored; nats.c needs OpenSSL and libsodium and does not fit ESP-IDF. One owner task runs the protocol loop and executes every call (`main/net/nats_glue.cpp`), so the C code never touches the C++ object from two tasks.
28. **Vendored patches to espidf-nats** (all marked `aiterm patch` in `nats_client.h`): (a) with JWT/NKey auth the library sent `jwt` and `sig` only; chronicle's identity bridge also needs `auth_token` (`<selector>:<github token>`) beside the sentinel JWT, so `send_connect()` adds it and the CONNECT buffer grew to 4 KB for the ~1 KB JWT; (b) the single-server (STARTTLS) path ignored `crt_bundle_attach` and ran TLS **without certificate verification** when no `ca_cert` was given — seen on the badge as "Certificate verification was skipped"; it now attaches the IDF bundle and requires verification exactly as the library's transport path does; (c) the text of the server's `-ERR` is kept in `last_server_error`, so an *Authorization Violation* can be told from anything else; (d) `NATS_MAX_ARGV` is 6, not 5 — `HMSG <subject> <sid> <reply-to> <hdr bytes> <total bytes>` has six tokens, and every JetStream delivery of a message with headers is exactly that (the ack subject is the reply-to); with five the length token was lost and every op was dropped silently, which is why the first live session sat at "reading the record" with nothing shown. Also: `connect()` returns once CONNECT is sent, before the auth callout answers (~250 ms); the glue therefore confirms a connection with a PING/PONG round trip before reporting success.
29. **GitHub device flow, not PKCE** — PKCE needs a callback URL registered on the GitHub App; a badge on a LAN address can never be one. The `chronicle` CLI already signs in with the device flow, so the App has it enabled; device-flow tokens refresh at GitHub with the client id alone, no secret on the device. Tokens live in the NVS config JSON, masked on export. **The code is shown on the badge as a QR**, not only on the setup page: the phone that runs the setup page sits on the badge's hotspot, where the captive DNS resolves every name to the badge, so it cannot reach GitHub; a QR of `github.com/login/device?user_code=…` is scanned from any network with internet. GitHub carries the parameter through its sign-in redirect (`return_to`); whether the device page fills the field from it is GitHub's business and was not confirmed — the first test on the badge found the field empty — so the code itself is the first thing on the screen, in the largest font, and in the view's status line. The flow itself runs on the badge, which must be on Wi-Fi first; the page's button is disabled until it is.
30. **NKey signing through the vendored wolfCrypt** — the sentinel is a decorated creds file (JWT + ed25519 seed); `HAVE_ED25519` was already on for wolfSSH, so `main/net/nkeys.c` decodes the base32/CRC16 seed and signs the server nonce with it. No libsodium.
31. **The transcript comes from the store's stream, not the derived state** — the KV state bucket holds `{seq,state}` without the author; `Op-Author` lives on the operation. One pull consumer over `LOG_<STORE>` with `CHRON.<store>.OPS.>`, **acknowledging nothing**: the account's member baseline does not allow publishing to `$JS.ACK.>` (chronicle's own readers are ordered consumers that never ack) and the first ack came back as a permissions violation. Should a server insist on an ack policy the badge falls back to explicit acks once; a sequence guard keeps redeliveries out of the model either way. Folded on the badge exactly like the hosted rooms page folds its tail (rooms, messages, `agent/<name>` announcements). After a reconnect the consumer starts from the last sequence seen. A pull window that closes with nothing new also counts as "caught up", so a wrong pending count can never leave the badge "reading the record" forever.
32. **Writes always take the verified route** (`CHRON.API.<principal>.APPLY.<store>.<tail>`, decision 0057 in chronicle-hq) — one core request/reply with the Op headers, no JetStream publish/ack handling on the badge, and it works whether or not the store demands verified authors. `instance-exists` on a create is read as "already there" for rooms and conversations.
33. **Rooms are rendered as the record, nothing is echoed locally** — a posted message appears when its operation comes back through the consumer (about a second), so the badge never shows a message the store did not accept.
34. **Power off = deep sleep below the IP5306's light-load threshold** — the carrier's power IC is an IP5306 power-bank chip (carrier schematic, `Carrier/power.kicad_sch`, netlist exported with kicad-cli 9.0.9); its KEY pin reaches only the power button (R15 → PWR_BUTTON1), so the P4 cannot switch the badge's 5 V rail, and the stock firmware (BadgeVMS, official and Tonemon fork) has no power-off either. The one software-reachable "off" is the IP5306's own light-load shutdown (standard IP5306: output off after 32 s under ~45 mA, from the cells). `bsp_power_off()` for the WHY2025 target (vendored BSP, `targets/why2025/badge_bsp_power.c`) sends DISPOFF + SLPIN to the ST7703, asserts the panel reset (GPIO 17), holds the C6 in reset (GPIO 12 low, RTC hold) — which also resets the TCA8418 and lets both AP3032 CTRL pins fall to their 100 kΩ pull-downs, because the backlights are driven by the C6's GPIO 15/10 PWM (set to 10 % by the stock slave at boot) and the P4 has no path to them (the R16 link from P4 GPIO 5 to DISPLAY_BL is DNP) — and enters deep sleep with no wake source. Wake is a reset: the IP5306 power cycle via the power button (cells), USB re-plug, or the CH340's DTR/RTS. Nothing else can wake it: the badge has no reset button (the M.2 card's EN and BOOT are driven only by the CH340's auto-reset transistors), and the TCA8418 INT line goes to the J7 header, not to the P4 — `BSP_KBD_INT` (GPIO 2) is in fact the USB mux select (`USB_CS`), which is why keyboard interrupts never fired (DECISIONS deviation 10). Confirmation is a second Enter on the Settings item; no dedicated key. Not verified on hardware yet: that the C6's GPIO 15 pad does not pull the display backlight up while the C6 sits in reset (if it does, the IP5306 will not trip and the fix is to populate R16 and hold GPIO 5 low).

## Hardware bring-up deviations from the upstream badge.team BSP (2026-10-17)
The vendored `components/badge-bsp` WHY2025 target (commit c663c68) differs from what the badge's
stock firmware (BadgeVMS) does on the real hardware. Each change below was made after observing the
failure on a production badge; keep them when updating the BSP.
7. **Panel in RGB565 + BGR** (`targets/why2025/badge_bsp_display.c`): the BSP's RGB888 gave vertical
   stripes and garbled rows; BadgeVMS runs 16-bit with BGR element order. LVGL at `LV_COLOR_DEPTH_16`.
8. **C6 reset via P4 GPIO 12, every boot** (`sdkconfig.defaults`): the BSP's callback reset is a no-op
   stub on this target and left the host in a reboot loop when the SDIO handshake was missed.
   GPIO 12 is the C6 EN line, GPIO 13 its BOOT line (BadgeVMS `slave_c6_flasher.c`).
9. **Keypad reconfigured after the radio reset** (`main/net/wifi.c` → `why_keyboard_configure()`):
   GPIO 12 also resets the TCA8418 (BSP_KBD_RST is -1), wiping its configuration.
10. **Keypad polled every 20 ms** (`components/tca8418`): the INT line (GPIO 2) never fires; BadgeVMS
    passes GPIO_NUM_NC and polls.
11. **Key events only on press, three space keys** (`targets/why2025/badge_bsp_input.c`): the BSP
    queued a character on release too and only knew key code 0x41 of the 0x41..0x43 space keys.
12. **Wi-Fi power save off after association**, not right after `esp_wifi_start()`: an early
    `esp_wifi_set_ps()` made the next `esp_wifi_set_config()` fail with ESP_ERR_WIFI_STATE on the
    2.0.17 slave. With power save on, ping RTT through the link was 1.6-12 s; off: 5-23 ms.
13. **Flashing keeps NVS**: `out/flash.sh` writes the parts at their offsets; the merged image
    pads 0x9000-0x19000 with 0xFF and erased the settings on every flash.
14. **Console on UART0** (side USB-C / CH340, `1a86:7522`, needs WCH's driver on macOS); the bottom
    USB-C is the C6's USB-Serial/JTAG.
15. **`bsp_power_initialize()` / `bsp_power_off()` implemented** (`targets/why2025/badge_bsp_power.c`,
    pins in `why2025_hardware.h`): power off is panel off + C6/keypad reset hold + deep sleep, see
    decision 34; init releases any GPIO hold left from it.
